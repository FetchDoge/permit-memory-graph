## 1. Method

A perf harness (`hidden_files/audit-2026-10-16/perf_harness.py`) measures
the slice's public API — `claim_spend` (allow path), cumulative-cap
refusals that cite D active claims, `provenance_for`, `neighbours`,
`revoke_permit` — at increasing graph sizes (up to 8,000 background
claims / 32,363 total nodes), on file-backed SQLite and on FalkorDB.
Bulk state is seeded with rows identical to what the API writes, in one
transaction (SQLite) or via the API (Falkor); every *measured* operation
goes through the public API. Numbers are means over 3–30 repetitions
(p50/p95 in the harness logs, same folder).

Environment honesty: absolute latencies are this VM's. Its workspace
disk fsyncs at ~85–100 ms — on tmpfs the identical claim costs 0.55 ms —
so read the **ratios** as the result and the absolutes as
hardware-priced. That fsync price is also why several findings are
structural (round trips × fsync) rather than algorithmic.

## 2. Baseline — where it actually hurt

Mean latency, ms (SQLite file-backed / FalkorDB durable):

| Workload | SQLite | FalkorDB |
|---|---:|---:|
| `claim_spend` allow, small graph | 814 | 166 |
| `claim_spend` allow, 8,000 claims in graph | 970 | 183 |
| `claim_spend`, permit already holds 1,000 active claims | 786 | 216 |
| Cumulative refusal citing 50 / 200 / 1,000 claims | 5,190 / 17,671 / **88,349** | 1,442 / 6,417 / **28,862** |
| `provenance_for`, 500 claims + 500 decisions | 261 | 1,430 |
| `neighbours`, out-degree 1,110 | 16.1 | 74.2 |
| `revoke_permit`, 10 / 100 / 500 active claims | 2,030 / 9,971 / **48,885** | 2,863 / 3,372 / **14,261** |

Diagnosis, both backends, no vibes:

1. **Per-write commits (SQLite).** Every `add_node`/`add_edge`/`set_prop`
   committed individually; one claim is ~10 writes ≈ 800 ms of fsync.
   Fan-out writes scale it linearly: a refusal citing 1,000 claims writes
   1,000 provenance edges = 1,000 commits = **88 s**. A revoke cascade
   is one commit per claim voided.
2. **Full-scan finds (SQLite).** `find()` deserialized every node of a
   label and filtered in Python — paid twice per admission.
3. **Per-row round trips (FalkorDB).** Each write is a query, each query
   an AOF fsync (~15–30 ms). Same fan-out disease: refusal at depth
   1,000 = 1,000+ queries = 28.9 s.
4. **No indexes anywhere (FalkorDB).** Every `find` and every `MERGE`
   scanned a whole label; `get_node` matched `{id}` with no label, so
   no per-label index could ever fire. Bulk-load throughput visibly
   degraded as the graph grew.
5. **Provenance loop waste.** `provenance_for` fetched the Permit node
   once per claim (309 lookups ≈ the entire 75 ms of a mid-size query),
   and Falkor's unlabeled endpoint match made its `neighbours` scan.

## 3. Changes kept — each with before/after and its test

### C1 — One transaction per operation + batched edge writes (SQLite)
`GraphStore` gains `transaction()` (unit of work) and `add_edges_batch()`.
SQLite defers commit to the outermost block exit (rollback on error);
`claim_spend`/`revoke_permit` run inside one transaction; `_record`
writes all provenance edges via one `executemany`.
- claim_spend: 814 → **86 ms** (9.5×)
- cumulative refusal ×1,000: 88,349 → **236 ms** (374×)
- revoke 500 claims: 48,885 → **224 ms** (218×)
- Test: `test_transaction_defers_commit_until_exit` — a second connection
  sees nothing until the block exits, then everything.

### C2 — SQL-side filtering + expression indexes + JOIN neighbours (SQLite)
`find()` filters via `json_extract` in SQL, backed by expression indexes
on `(label, permit_id, status)` and `(label, scope, merchant_id)`; the
Python check remains as a verification net on the filtered subset.
`neighbours()` resolves destination nodes in one JOIN, not N+1 queries.
- claim_spend at 8,000 claims: 204 → **103 ms**, and the scaling curve
  flattens (86 → 103 ms from 0 → 8,000 claims; baseline grew 814 → 970
  and worsened beyond that)
- `provenance_for` (500+500): 187 → **11.8 ms**
- Tests: `test_find_matches_booleans_and_multi_props`,
  `test_neighbours_returns_joined_dst_nodes`.

### C3 — FalkorDB indexes + label-hinted lookups
The store creates indexes at connect: `(id)` for all five labels +
`Claim(permit_id)`, `Claim(scope)`, `Decision(scope)`,
`Decision(idem_key)` (added in C5). Domain call sites pass the label
they already know (`get_node(..., label="Permit")`, etc.).
A/B on one frozen 14,256-node graph, indexes on vs dropped:
- duplicate-check find (`Claim` by scope+merchant): 3.71 → **0.22 ms** (17×)
- `add_node` insert at ~12k claims: 29.8 → **16.2 ms** (the `(id)` index
  halves MERGE cost; the gap grows with label size)
- hinted Permit lookup: 1.32 → **0.24 ms** per call — multiplied by every
  claim in a provenance result, this was the real provenance cost
- admission latency: index-insensitive within noise (185–238 ms across
  full/trimmed/none) — indexes neither help nor hurt the fsync-bound
  write path, so the set is kept for the reads and the inserts.
- Two candidate indexes (`Claim(status)`, `Claim(merchant_id)`) were
  dropped from the set: no measured benefit; those filters run cheaply
  on the already-narrowed subset.
- Tests: `test_falkor_indexes_created`, `test_falkor_label_hint_lookup`
  (in `test_falkor_optional.py`, runs when a server is up).

### C4 — Batched edges + bulk cascade + provenance dedupe (FalkorDB path)
`add_edges_batch` issues one UNWIND query per relationship type, with
endpoint label hints so each row matches through the `(id)` index.
`update_where` (new store primitive) sets a property on all matching
nodes in ONE statement — the revoke cascade is now a single Cypher /
single SQL UPDATE instead of one call per claim. `provenance_for`
dedupes permit ids from the claims before fetching (one lookup per
distinct permit, not per claim).
- cumulative refusal (Falkor, targeted re-measure after label hints;
  full-graph finals in §4): ×50: 1,442 → **72 ms**; ×200: 6,417 →
  **100 ms**; ×1,000: 28,862 → **150 ms** (192×)
- `provenance_for` (Falkor, harness graph): 1,430 → **50 ms** (29×)
- revoke (Falkor, targeted): the depth scaling is gone — 101 / 90 /
  66 ms at 10 / 100 / 500 claims (baseline grew 2,863 → 14,261 ms)
- SQLite revoke 500 after C1+C2+C4: 48,885 → **89 ms** final
- Tests: `test_provenance_fetches_each_permit_once`,
  `test_update_where_flips_only_matching`,
  `test_falkor_add_edges_batch`, `test_falkor_update_where`.

### C5 — Feature: idempotent claims
`claim_spend(..., idempotency_key=...)`: the Decision node records the
key and its provenance; a retry replays the recorded decision verbatim
(same decision id, allowed/refused as originally decided, zero new
writes) instead of being re-decided against current state. This is a
Permit-shaped guarantee — a spend that timed out on the wire must not
come back as a second spend or a spurious duplicate refusal.
- Cost when keyed: +7.7 ms (Falkor, one indexed find) / +0.2 ms (SQLite);
  zero when no key is passed.
- Replay cost: **0.44 ms** vs ~136 ms for a fresh decision (Falkor).
- Test: `test_idempotent_retry_replays_original_decision` (allowed and
  refused replays; graph stats unchanged by a retry; a different key is
  a new operation).

### C6 — Feature: structured refusal codes + provenance pagination
Every `Decision` now carries a machine-readable `reason_code`
(`ALLOWED`, `PERMIT_NOT_LIVE`, `PERMIT_EXPIRED`, `DUPLICATE_SCOPE`,
`OVER_CAP`, `CUMULATIVE_CAP_EXCEEDED`) alongside the prose reason, so
agents branch on a code instead of string-matching prose. The code is
stored on the Decision node and survives idempotent replay.
`provenance_for(scope, merchant, limit=None, offset=0)` returns history
in stable chronological order with `total_claims`/`total_decisions`
alongside, so callers page instead of materializing everything.
- Pagination latency effect is honest-small (SQLite full 10.4 → page-of-10
  6.5 ms; Falkor 65.9 → 54.9 ms at 500+500): the store still reads the
  history; the win is bounded payload and caller work, plus totals.
- Tests: `test_reason_codes_on_every_path`,
  `test_provenance_pagination`.

## 4. Final numbers (after all changes)

Mean latency, ms — baseline → final:

| Workload | SQLite | FalkorDB |
|---|---:|---:|
| `claim_spend` allow, small graph | 814 → **87** (9.4×) | 166 → **147** (1.1×) |
| `claim_spend` allow, 8,000 claims | 970 → **105** (9.2×) | 183 → **182** (≈flat) |
| `claim_spend`, permit holds 1,000 active | 786 → **103** (7.7×) | 216 → **210** (≈flat) |
| Cumulative refusal ×50 / ×200 / ×1,000 | 5,190 → **93** · 17,671 → **118** · 88,349 → **127** (up to 698×) | 1,442 → **96** · 6,417 → **80** · 28,862 → **155** (up to 186×) |
| `provenance_for` 500+500 | 261 → **6.7** (39×) | 1,430 → **59** (24×) |
| `neighbours` out-degree 1,110 | 16.1 → **9.5** (1.7×) | 74.2 → **71** (≈flat) |
| `revoke_permit` 10 / 100 / 500 | 2,030 → **83** · 9,971 → **80** · 48,885 → **89** (up to 549×) | 2,863 → **129** · 3,372 → **83** · 14,261 → **75** (up to 190×, now flat in D) |

Read the Falkor admission row honestly: admission barely moved,
because its floor is ~5 write queries × one AOF fsync each — the
durability price priced in §5. What the audit removed on Falkor is
every *fan-out* cost (refusals, cascades, provenance reads), where the
baseline grew linearly with graph history and the final code is flat.
On SQLite the same structural fixes also cut the base admission cost
~9×, because there the per-write commit was the admission cost.

## 5. Tried and rejected

- **SQLite WAL + `synchronous=NORMAL`** — 2.2× on the claim bench
  (0.55 → 0.25 ms, tmpfs). REJECTED as the shipped default: NORMAL can
  lose the most recent committed transactions on an OS crash/power
  loss. This product's benchmark case B7 *is* crash-survival of the
  record; we do not buy speed with the guarantee being sold. Noted as
  an operator knob for deployments that accept the trade.
- **FalkorDB `--appendfsync everysec`** — claim_spend 135.9 → **5.9 ms**
  (23×). REJECTED, same reason, quantified: ~130 ms of every durable
  claim on this disk is the fsync price of zero-loss durability. With
  everysec, a kill can silently lose up to ~1 s of acknowledged
  decisions — B7's seeded claim could vanish and the benchmark would
  still call the system healthy. We pay the 130 ms deliberately.
- **In-memory cumulative-sum cache** (admission-path memoization) —
  considered, **not implemented**: a cache between the graph and the
  cap check reintroduces exactly the stale-view race Permit's PR #41
  (single ordered record) and PR #20 (cumulative cap) exist to kill.
  The graph is consulted at decision time, every time; C2/C3 made that
  consultation cheap instead of optional.
- **`Claim(status)` / `Claim(merchant_id)` indexes** — created,
  measured, dropped from the set (see C3): no measurable gain on any
  workload; dead index weight on every insert.

## 6. Operational finding (from this audit's own machinery)

Repeated CREATE/DROP INDEX cycles against a live AOF (my A/B scripts
churning indexes on the scratch perf graph) left an effect the server
could not replay: on restart FalkorDB logged `Diverged applying
GRAPH.EFFECT on graph 'permit_memory_perf': Unable to drop index on
:Claim(id): no such index` and shut down. Recovery was wiping the
scratch data dir. Two lessons recorded: (1) treat index churn on a
live AOF as unsafe on this build — the shipped code only ever CREATEs
indexes (idempotently) and never drops them at runtime; (2) the frozen
benchmark's own data dir was never exposed to this — run 2's B7 result
is unaffected.
